# FW1 review: firmware arm timeout (`feature/connector-fw1`)

FW1.3 grill review, 2026-10-07. One attacker (independent reviewer, read-only, with a differential Core-vs-FakeMcu
fuzz), plus a mutation check by the implementer. **Verdict: APPROVE** after the fixes below. The first pass said
REQUEST_CHANGES (3 SHOULD-FIX, no BLOCKING).

Scope: `firmware/watchdog_mcu/{main.py,PROTOCOL.md,README.md,test_vectors.json}`, `src/so101_rl/servo/heartbeat.py`,
`tests/test_firmware_vectors.py`, `tests/test_heartbeat.py`, and `docs/HARDWARE_CHECKLIST.md` H3 step 10.

## Attacker brief: answers

- **Can a press leave the relay closed, or close it again?** No. The relay is `state == ARMED`, recomputed every
  loop. Only an accepted `0x5A` enters ARMED. The button acts only on LATCHED, and its only effect is LATCHED →
  DISARMED. The arm timeout only ever trips to LATCHED. A button held through the timeout leads back to DISARMED,
  not to ARMED (vector `button_held_through_arm_timeout_only_returns_to_disarmed`).
- **Can serial traffic extend the 120 s window?** No. `dt` is written in exactly one place, DISARMED entry. Nothing
  in `feed` touches it: STATUS, heartbeats, noise, stalled partial frames and refused ARMs are all inert. Pressing
  the button while DISARMED does not restart the window either. Pinned by `serial_traffic_does_not_extend_arm_window`
  (portable), `arm_refused_by_undervolt_does_not_extend_arm_window` and
  `button_while_disarmed_does_not_restart_arm_window`.
- **Is the wrap handled?** Yes. The check uses `self.d(now, self.dt)`, which is `ticks_diff` on the MCU. 120 000 ms is
  far inside the ±2**29 ms unambiguous range. A DISARMED state cannot outlive the window, because it latches first,
  and the 250 ms WDT keeps `poll` running. `wrap_safe_arm_timeout_30bit` puts the 2**30 wrap inside the window.
- **Does any existing vector change meaning?** Only `disarmed_never_times_out`, as planned. It is renamed to
  `disarmed_119999ms_still_disarmed` and shortened to 119 999 ms. Every other vector keeps DISARMED for less than
  6 s. With the check removed (mutant FM1), every pre-existing vector still passes.
- **Is the reason nibble ≤ 15, and decoded everywhere?** Yes. 8 → `0x82` / `0x80`. On the host,
  `REASON_ARM_TIMEOUT`, `REASON_NAMES` and `McuStatus.reason_name` were added; an unknown nibble decodes as
  `UNKNOWN_<n>` and never raises. The invariants test bound is now ≤ 8 and checks every status byte, not only the
  first. Other consumers are hand-offs (see below).

## Findings and resolution

1. **SHOULD-FIX: Core and FakeMcu drift when the button is held through the timeout. FIXED.**
   The plan placed the check "right after the button rows". In that position Core starts the 500 ms hold one poll
   after the latch. FakeMcu re-polls inside `feed()` at the same instant, so it starts the hold at the latch tick.
   With sparse polls the gap grows without bound: in a random differential fuzz FakeMcu armed where Core refused.
   - **Fix:** the check now sits right after the ARMED trip rows and before the button rows, in both `Core.poll`
     and `FakeMcu._poll`. This is where the heartbeat TIMEOUT already sits, so both models start the hold at the
     latch tick.
   - **Effect:** the vector now pins `0x80` at exactly latch + 500 ms. Mutant FM13 (the plan's literal placement)
     fails on it.
   - **Unchanged:** the line count (93) and the timeout semantics.
   - **Placement and outputs:** the check runs before the button rows, but a DISARMED entry in the same poll has
     diff 0, so no output changes.
   - **Fuzz after the fix:** 166 diverging random sequences, against 149 with the arm timeout disabled. All of
     them are the pre-existing harness drift in item 6. No shipped vector diverges.
2. **SHOULD-FIX: `docs/ARCHITECTURE.md` has no reason 8 row, no two-timer rule and no §10 row. HANDED TO THE
   MASTER.** This executor was told not to edit ARCHITECTURE. The exact delta text is in the FW1 hand-off report.
   It must land in the same commit series as FW1 (CLAUDE.md, FW1.4).
3. **SHOULD-FIX: H3 has no pass criterion for the arm timeout. FIXED** inside step 10: "Pass: latch at 120 ± 1 s with
   `0x82` and the relay open throughout; the re-press gives `0x80`; the ARM gives `0x05`". The shared H3 Pass line
   was left untouched, because only step 10 and the artifact field belong to FW1.
4. **NIT: `FakeMcu.reset_button` window start. FIXED + documented.**
   - **Was:** the window started when the helper returned (press + `hold_ms`).
   - **Now:** it starts at press + 500 ms, as in the firmware (`test_fakemcu_reset_button_longer_hold_starts_window_at_the_500th_ms`).
   - **Documented:** the docstring says the helper assumes the button was released beforehand and
     `hold_ms < ARM_TIMEOUT_MS`. For a button held across a latch, use `set_button`.
5. **NIT: the PROTOCOL claim "an ARM at exactly 120 000 ms is refused" holds only in loop-tick time. FIXED** (text:
   "judged at the loop tick in which its byte is drained, as for every serial frame").
6. **NIT: FakeMcu is proven byte-identical only on the curated vectors. DOCUMENTED** in the `run_vector_fake`
   docstring.
   - **Cause:** the replay applies the setters one at a time, and each one runs the loop body with the inputs
     only partly applied. `feed` also re-polls.
   - **Size:** this drift is pre-existing (149 fuzz divergences without FW1).
   - **Follow-up, not FW1:** a setter-free `FakeMcu.step(inputs)`.
7. **NIT, hand-off to SV1: `servo/core.py:401,437` print `reason {st.reason}`.** They should print
   `st.reason_name`, for example "ARM_TIMEOUT: press the button again". `core.py` belongs to SV1.
   - **Behaviour:** `_wait_for_arm` already treats a reason-8 latch like any latch ("press the physical reset
     button").
   - **Summary and dashboard:** the summary's `first_mcu_status`/`last_mcu_status` (SV1) and the dashboard (LA4)
     should show `reason_name`.
   - **Two-phase verdict:** `weld_ok` (FL12) already accepts reason 8.

Also checked, and found to hold:

- `SimulatedOperatorLink`, `env/backend.py` and `sysid/run_excitation.py` all ARM within a tick of DISARMED.
- No test or fake path parks a FakeMcu in DISARMED for 120 s. The full suite passes unchanged.
- `--arm-timeout-s` still defaults to `None` (`servo/main.py:88`).

`tests/test_servo_process.py::test_arm_timeout_cli_default_is_none`, named in A10, does not exist yet. Its file
belongs to SV1, so it is a hand-off.
